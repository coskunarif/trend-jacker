# SPEC.md - Topic-Based Trend Analysis Caching

## Background & Goal
To decrease Gemini API billing costs, trend analysis explanations (generated by the Gemini API) must be cached by topic (trend name). Subsequent requests for the same topic must retrieve the cached explanation from a persistent store rather than invoking the Gemini API. Sentiment vote data (polls) must remain dynamic and up-to-date in the returned results.

## Acceptance Criteria

### `[AC-1]` Caching of Trend Explanations
- **Requirement**: Explanations generated by Gemini API must be cached by topic (trend name). A subsequent lookup for the same topic must return the cached values (hook, whatIsIt, whyIsItViral, takeaway) instead of querying the Gemini API.
- **Verification**: Querying the explanation of a trend twice should result in only one generative model invocation (or mocked invocation). Modifying the cached database value directly and querying again will return the modified value, proving it was served from the cache.

### `[AC-2]` Persistent Cache Storage
- **Requirement**: Caching must survive server restarts by using the database:
  - **SQLite (Local/Dev/Test)**: A new table `trend_explanations` is created with schema:
    ```sql
    CREATE TABLE IF NOT EXISTS trend_explanations (
      trend TEXT PRIMARY KEY,
      explanation TEXT, -- JSON-stringified object
      created_at TEXT
    )
    ```
  - **Firestore (Production)**: Document `trend` in collection `trend_explanations` containing fields: `hook` (string), `whatIsIt` (string), `whyIsItViral` (array of strings), `takeaway` (string), and `created_at` (string).
  - **In-Memory Map Fallback**: Active if SQLite database cannot be loaded in local mode.
- **Verification**: The schema is successfully created when the application starts, and the cache data is written to the database.

### `[AC-3]` Live Dynamic Sentiment Poll Integration
- **Requirement**: Sentiment poll statistics (genius vs. overrated percentages/counts) must not be statically cached. On every request for a trend explanation, the dynamic sentiment vote counts must be retrieved live from the database and merged with the cached explanation data.
- **Verification**: Set a trend explanation in the cache. Query it to verify poll values. Submit a vote to change poll values. Query the trend explanation again; the returned `polls` field must reflect the updated count.

## Out of Scope
- Caching follow-up interactive chat sessions (`/api/chat`) or customized social post generations (`/api/generate-post`), as these are customized per user query/context.
- Advanced cache eviction policies (like LRU/LFU limits) or expiration/TTL policies, since a permanent topic cache matches the "show all the time for same topic" billing optimization.

## Slices

### `[S-1]` Database Tier Updates
- **Files**:
  - `db.js`
- **ACs Mapped**: `[AC-2]`
- **Description**: Add schema migration for SQLite table `trend_explanations`. Expose two functions:
  - `getCachedExplanation(trend)`: retrieves cached explanation (parsing JSON string for SQLite/in-memory or returning Firestore doc fields).
  - `setCachedExplanation(trend, explanation)`: persists the explanation fields (hook, whatIsIt, whyIsItViral, takeaway) to SQLite, Firestore, or in-memory.
- **Test Strategy**: Add unit tests in `tests/caching.spec.js` testing these functions directly.
- **Dependencies**: None.

### `[S-2]` Server & Explanation Caching Integration
- **Files**:
  - `server.js`
- **ACs Mapped**: `[AC-1]`, `[AC-3]`
- **Description**: Refactor `getTrendExplanation(trend, headline, snippet)` to:
  1. Check the cache database first using `getCachedExplanation(trend)`.
  2. If found, retrieve the live poll statistics via `getPollData(trend)`, assign to `explanation.polls`, and return.
  3. If not found, run the existing Gemini model logic (or test mock), write the generated explanation to the cache using `setCachedExplanation(trend, explanation)`, retrieve live poll statistics, and return.
- **Test Strategy**: Integration tests verifying that caching functions correctly for `/api/explain` and `/t/:slug`.
- **Dependencies**: `[S-1]`

### `[S-3]` E2E Caching Verification Tests
- **Files**:
  - `tests/caching.spec.js`
- **ACs Mapped**: `[AC-1]`, `[AC-2]`, `[AC-3]`
- **Description**: Add comprehensive Playwright E2E and integration tests verifying:
  - Successive hits to `/api/explain` use the cache (verified by checking db inserts/updates or modifying the database value between hits).
  - Submitting a vote updates the poll data in subsequent explanation returns.
- **Test Strategy**: Tests first, validating functionality on the local SQLite DB.
- **Dependencies**: `[S-2]`
